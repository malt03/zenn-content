## 最初に断っておきます

これはポエムです。

自分は法律家ではないし、以下の話は全部「こうなんじゃないの？」という思いつきであって、なんの確信はありません。ライセンスの条文と判例を眺めながら、思ったことを書いてみただけです。詳しい人がいたらツッコミをもらえると嬉しいです。

## LLMにMastodonのコードを思い出させてみた

ふと思い立って、Claudeに「インターネットを検索せず、Mastodonのコードを出力して」と頼んでみました。MastodonはAGPLライセンスの、そこそこ有名なコードベースです。

そうしたら、Snowflake風のID生成をするPostgreSQLの関数とか、ホームタイムラインをRedisにfan-out on writeするFeedManagerとか、ActivityPubの受信処理とかが、かなりそれらしい形で出てきました。しかも `delete_arrived_first?` みたいな、解説記事にはまず出てこない地味な内部メソッド名まで出てくる。定数の一部は現行のコードとは違う、旧バージョンの値だったりもしました。

これつまり、モデルの中にMastodonのコードが何らかの形で残っている、ということですよね。

## テンソルは「コピー」なんじゃないか

ここで素朴な疑問が湧きます。

ソースコードを、復号可能な形で暗号化して配布したらどうなるでしょう。人間には読めないバイナリ列になっていても、著作権上の「複製物の配布」なのは明らかだと思います。

そしてLLMについては、簡単なプロンプトで、人間には解読不能な形でテンソルに埋め込まれたコードを「復号」できるわけです。

だとすると、**モデル（の重み）は、抽出可能な範囲において、学習したコードのコピーを内包している**と言えるんじゃないでしょうか。

## じゃあAGPLのモデルは公開義務があるのでは

GPLの継承義務は、基本的に「配布（convey）」したときに発動します。社内で使っているだけなら何も起きない。

問題はAGPLです。AGPLの13条は、ざっくり言うと「改変したプログラムをネットワーク越しに他人が使える形で提供するなら、そのソースコードを入手する手段を提供しなければならない」という条項で、SaaSの抜け穴を塞ぐために作られました。

LLMをAPIで提供するのは、まさにこれです。

モデルがAGPL著作物に基づく著作物で、それをネットワーク越しに対話可能な形で提供している。だったら13条の義務が発生して、対応するソースを公開しなきゃいけないのでは……？

これがこのポエムの主張です。条文の文面だけ読むと結構筋が通っている気がします。

## 留保

……と、勢いで書きましたが、留保はたくさんあります。

**留保1：抽出できるのは一部だけ。** 暗号化には決定論的な復号手順があって平文が100%戻りますが、学習は損失の大きい圧縮です。何度も重複して現れる有名なコードは強く暗記されますが、一度しか現れない無名のコードは復元できません。「テンソルの中にソースが入っている」は、有名なごく一部のコードに対して言えるだけです。

**留保2：「コピーを含む」≠「モデル全体がGPLを継承する」。** 同じ重みの中には、GPLv2もGPLv3もApacheも、商用ライセンスのコードの断片も、全部混ざっているはずです。互いに両立しない義務を全部同時に継承するのは原理的に無理で、裁判になったとしても「モデル全体がAGPLになる」というより、著作物ごとの侵害と救済の話になる公算が大きいと思います。

**留保3：モデルの「対応ソース」って何？** GPLの言うCorresponding Sourceは「オブジェクトコードを生成・実行するために必要なもの」です。モデルに当てはめると学習コード＋学習データ＋手順、みたいな読みが自然ですが、学習データ全部となると他人の著作物や個人情報を含んでいて公開不可能です。GPLの論理では「履行できないなら提供自体をするな」という帰結になるんでしょうか。

## 参照すべき判例とか

この話、調べてみると自分が思いついた新説でもなんでもなくて、周辺では結構議論も裁判も起きているようです。
以下、LLMに調べてもらった判例です。

**GEMA v. OpenAI（ミュンヘン地方裁判所、2025年11月11日）。** 一番近い到達点だと思います。対象はコードではなく歌詞ですが、裁判所は「歌詞がモデルのパラメータに分散して埋め込まれていても、プロンプトで取り出せる以上、暗記自体が複製にあたる」と認定しました。類比として持ち出されたのがMP3の損失圧縮で、自分の暗号化の類比とほぼ同じ発想を裁判所が採用した形です。ただしOpenAIは控訴中です。

**米著作権局の2025年5月の報告書。** 「プロンプトが与えていない表現が逐語的に出力されるなら、その表現は重みの中に何らかの形で存在するはずであり、重みの複製が複製権に触れる強い議論がある。鍵は実質的な保護可能表現を保持しているかどうか」という整理で、論点の設定としては自分の疑問とかなり近いものでした。

**Doe v. GitHub。** Copilotへの集団訴訟（2022年〜）。主戦場は出力側で、帰属表示の除去（DMCA §1202）の請求は2026年9月に第9巡回区控訴裁でも棄却が維持されました。ライセンス違反の契約請求は地裁で継続中。重みそのものを争った事件ではありません。

そして議論の本流としては、Software Freedom ConservancyのBradley Kuhnが2021年のCopilot発表直後から、ほぼ同じ構造の批判を続けています。新説でも何でもなかった、というのが調べてみた正直な感想です。

## とはいえ、誰も訴えないと思う

書いておいてなんですが、訴える側のインセンティブがないのでこの訴訟は起きないと思っています。

- 勝っても得られるのは差止めとコンプライアンスだけで、売っているOSSでもなければお金になりづらい
- 非営利団体や個人が、巨大IT企業を相手に何年も訴訟を続ける資金がない。負ければ「重みは複製ではない」という判例が固定して、コピーレフト全体が後退する

事業者側としても、訴えられる前に学習データからコピーレフトのコードを除く、重複を除去する、出力にフィルタをかける、という対応をしてしまうコストはそこまで高くない。

AGPLといえばMongoDBですが、その事例と比較すると見えてくるものがあります。

MongoDB vs SaaS の時は双方に争うインセンティブがありました。事業者は「MongoDBそのもの」を欲しいし、MongoDB側にはそれを訴訟してでも差し止める価値があった。
LLMが欲しいのは「コード一般」であって、特定の誰かのコードではない。個別の権利者には原理的に交渉力がない。
そもそもエンジニアの多くは今のLLMの発展を止めたいインセンティブもないし、止められるとも思っていない。

一方で、LLMの場合にMongoDBと違うのは、相手のデータセンターの中身は見えなくても、モデルの中身はプロンプトで外から検査できることです。冒頭のMastodonの再現実験がまさにそれで、立証手段という点では、権利者はMongoDBのときより恵まれているとは思います。

なんにせよ、仮に最高裁で「重みは二次的著作物です」と確定したとしても、起きるのは「分かりました、次世代の学習データから抜きますね」くらいで、フラッグシップモデルの重みが公開されたり、サービスが差し止められたり未来はあまり見えません。

## おわりに

というわけで、法理としては筋が通っている気がするし、裁判所が歌詞で一度認めた論法でもあるけれど、訴訟するインセンティブが誰にもないので、なんとも言えないよねぇ、という話でした。

そもそも私もLLMの恩恵を超享受して生きている人間ですから、差し止められて欲しいわけでもありませんし。

ポエムなので結論はありません。詳しい方のツッコミや「その判例はこう読むべき」みたいな話があれば歓迎です。

インターネットには接続せず、私の記憶だけでお答えします。以下のコードは記憶からの再現なので、細部(定数値や行単位の書き方)は現行のリポジトリと違う可能性があります。

#### 全体構成

Mastodon は Ruby on Rails のモノリスを中心に、次の部品で動いています。

- **Rails**: REST API、ActivityPub の受信、管理画面
- **Sidekiq**: 配送や連合などの非同期処理
- **Node.js の streaming サーバー**(`streaming/`): WebSocket / SSE でタイムラインをリアルタイム配信
- **React + Redux**(`app/javascript/mastodon/`): Web UI
- **PostgreSQL と Redis**: 永続データと、タイムライン・Pub/Sub

#### 1. Snowflake 風の ID 生成(`lib/mastodon/snowflake.rb`)

投稿 ID は連番ではなく、PostgreSQL の関数で「時刻 48bit + シーケンス 16bit」として生成されます。

```sql
CREATE OR REPLACE FUNCTION timestamp_id(table_name text)
RETURNS bigint AS $$
  DECLARE
    time_part bigint;
    sequence_base bigint;
    tail bigint;
  BEGIN
    -- ミリ秒のタイムスタンプを 16bit 左シフト
    time_part := ((date_part('epoch', now()) * 1000))::bigint << 16;

    -- テーブル名 + 秘密のソルト + 時刻の MD5 から先頭 2 バイトを取る
    sequence_base := (
      'x' || substr(md5(table_name || '<salt>' || time_part::text), 1, 4)
    )::bit(16)::bigint;

    -- シーケンスを足して下位 16bit だけ残す
    tail := (sequence_base + nextval(table_name || '_id_seq')) & 65535;

    RETURN time_part | tail;
  END
$$ LANGUAGE plpgsql VOLATILE;
```

ID が時系列順に並ぶので、`max_id` / `since_id` によるページネーションが ID 比較だけで済みます。下位ビットをハッシュで攪乱しているのは、ID から「そのサーバーの投稿数」を推測されないためです。

#### 2. ホームタイムラインは Redis への fan-out on write(`app/lib/feed_manager.rb`)

投稿時にフォロワー全員の Redis sorted set へ ID を書き込む方式で、読み込み時に JOIN しません。

```ruby
class FeedManager
  MAX_ITEMS = 400
  REBLOG_FALLOFF = 40

  def key(type, id, subtype = nil)
    return "feed:#{type}:#{id}" unless subtype
    "feed:#{type}:#{id}:#{subtype}"
  end

  def push_to_home(account, status, update: false)
    return false unless add_to_feed(:home, account.id, status,
                                    aggregate_reblogs: account.user&.aggregates_reblogs?)

    trim(:home, account.id)
    PushUpdateWorker.perform_async(account.id, status.id, "timeline:#{account.id}",
                                   { 'update' => update }) if push_update_required?("timeline:#{account.id}")
    true
  end
end
```

- フィードは 1 人あたり約 400 件で切り詰められます。
- `REBLOG_FALLOFF` は、直近 40 件以内に同じ投稿のブーストがあれば重複表示しないための値です。
- `push_update_required?` で、ストリーミング接続中の人にだけリアルタイム通知を飛ばします。

呼び出し側の `FanOutOnWriteService` は、フォロワーをバッチに分けて `FeedInsertWorker.push_bulk` で Sidekiq に流します。

#### 3. ローカルとリモートを同じテーブルで扱う(`app/models/account.rb`)

```ruby
def local?
  domain.nil?
end

def acct
  local? ? username : "#{username}@#{domain}"
end
```

`accounts` テーブルに自サーバーと他サーバーのユーザーが同居し、`domain` が NULL かどうかだけで区別します。ログイン情報は別の `users` テーブルにあり、ローカルアカウントだけが持ちます。

#### 4. ActivityPub の受信処理(`app/lib/activitypub/activity/`)

受信した JSON の `type` ごとにクラスが分かれています(`Create`、`Announce`、`Follow`、`Delete`、`Undo` など)。

```ruby
class ActivityPub::Activity::Create < ActivityPub::Activity
  def perform
    return reject_payload! if unsupported_object_type? || non_matching_uri_hosts?(@account.uri, object_uri)

    with_redis_lock("create:#{object_uri}") do
      return if delete_arrived_first?(object_uri)
      @status = find_existing_status
      process_status if @status.nil?
    end
    @status
  end
end
```

連合ならではの防御が入っています。

- **Redis ロック**: 同じ投稿が複数経路から同時に届いても二重に作らない
- **`delete_arrived_first?`**: Delete が Create より先に届く順序逆転に対応する
- **URI のホスト照合**: 他人になりすました投稿を拒否する

#### 5. HTTP Signatures と SSRF 対策(`app/lib/request.rb`)

サーバー間リクエストはアカウントの RSA 鍵で署名されます(`Signature` ヘッダー)。受信側は `SignatureVerification` concern で検証します。

また、リモート URL を取得するとき、名前解決した IP がプライベートアドレスなら接続を拒否します(`PrivateAddressCheck`)。ユーザー入力の URL を取りに行く連合ソフトでは必須の仕組みです。

#### 6. 配送ワーカーのリトライ設計(`app/workers/activitypub/delivery_worker.rb`)

```ruby
class ActivityPub::DeliveryWorker
  include Sidekiq::Worker
  sidekiq_options queue: 'push', retry: 16, dead: false
end
```

相手サーバーが落ちている前提で、指数バックオフで長期間リトライします。Stoplight によるサーキットブレーカーと、`DeliveryFailureTracker` による「何日も失敗が続くサーバーは配送対象から外す」処理が組み合わされています。

#### 7. その他の特徴的な箇所

- **`Status` の `visibility` enum**: `public` / `unlisted` / `private` / `direct` / `limited` の 5 種類で、公開範囲の判定はここが基準です。
- **`StatusLengthValidator`**: 上限は 500 文字で、URL は長さに関わらず 23 文字として数えます。
- **`PostStatusService`**: `Idempotency-Key` ヘッダーを Redis に記録し、二重投稿を防ぎます。
- **streaming サーバー**: Redis の `timeline:<account_id>` チャンネルを購読し、WebSocket にそのまま中継します。
- **Blurhash**: 画像のぼかしプレースホルダーを文字列で保持します。

特定の領域(連合、タイムライン、フロントエンド、モデレーションなど)をさらに掘り下げることもできます。正確なコードが必要な場合は、リポジトリを手元に clone してもらえれば実物を読みながら解説します。
```
